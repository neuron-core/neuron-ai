# Neuron tables in a Doctrine migration

`SQLMessageStore` needs `chat_messages` and `DatabasePersistence` needs `workflow_store`. Neither table is an entity, so the ORM never creates them: one hand-written migration does, with the DDL core documents in the docblocks of both classes (`vendor/neuron-core/neuron-ai/src/Chat/History/SQLMessageStore.php`, `vendor/neuron-core/neuron-ai/src/Workflow/Persistence/DatabasePersistence.php`).

Generate the file with `php bin/console doctrine:migrations:generate`, then fill it:

```php
namespace DoctrineMigrations;

use Doctrine\DBAL\Platforms\AbstractMySQLPlatform;
use Doctrine\DBAL\Platforms\PostgreSQLPlatform;
use Doctrine\DBAL\Platforms\SQLitePlatform;
use Doctrine\DBAL\Schema\Schema;
use Doctrine\Migrations\AbstractMigration;

final class Version20260929230146 extends AbstractMigration
{
    public function getDescription(): string
    {
        return 'Neuron AI conversation history (chat_messages) and run store (workflow_store)';
    }

    /** MySQL and MariaDB commit DDL implicitly: a wrapping transaction would already be closed. */
    public function isTransactional(): bool
    {
        return false;
    }

    public function up(Schema $schema): void
    {
        $platform = $this->connection->getDatabasePlatform();

        if ($platform instanceof AbstractMySQLPlatform) {
            // MySQL and MariaDB: IDs compare as bytes (VARBINARY, ascii_bin), never case- or accent-insensitively.
            $this->addSql('CREATE TABLE chat_messages (
                id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
                thread_id VARBINARY(255) NOT NULL,
                message_id VARBINARY(64) NOT NULL,
                role VARCHAR(32) NOT NULL,
                content LONGTEXT NULL,
                meta LONGTEXT NULL,
                archived_at DATETIME NULL,
                created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
                updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
                UNIQUE INDEX idx_thread_message (thread_id, message_id)
            ) ENGINE=InnoDB');
            $this->addSql('CREATE TABLE workflow_store (
                `partition` VARCHAR(510) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
                `key` VARCHAR(510) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
                `value` LONGTEXT CHARACTER SET ascii NOT NULL,
                updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
                PRIMARY KEY (`partition`, `key`)
            ) ENGINE=InnoDB');

            return;
        }

        $this->abortIf(
            !$platform instanceof PostgreSQLPlatform && !$platform instanceof SQLitePlatform,
            'Neuron stores support MySQL, MariaDB, PostgreSQL and SQLite.',
        );

        $id = $platform instanceof PostgreSQLPlatform ? 'BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY' : 'INTEGER PRIMARY KEY AUTOINCREMENT';
        $this->addSql("CREATE TABLE chat_messages (
            id {$id},
            thread_id VARCHAR(255) NOT NULL,
            message_id VARCHAR(64) NOT NULL,
            role VARCHAR(32) NOT NULL,
            content TEXT NULL,
            meta TEXT NULL,
            archived_at TIMESTAMP NULL,
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
            updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
            UNIQUE (thread_id, message_id)
        )");
        $this->addSql('CREATE TABLE workflow_store (
            "partition" VARCHAR(510) NOT NULL,
            "key" VARCHAR(510) NOT NULL,
            "value" TEXT NOT NULL,
            updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
            PRIMARY KEY ("partition", "key")
        )');
    }

    public function down(Schema $schema): void
    {
        $this->addSql('DROP TABLE chat_messages');
        $this->addSql('DROP TABLE workflow_store');
    }
}
```

Why each choice:

- **Exact ID comparison.** MySQL and MariaDB default collations ignore case and accents, so `user-Alice` and `user-alice` would share a history while getting two run partitions. `VARBINARY` IDs and `ascii_bin` keys compare bytes. PostgreSQL and SQLite compare `VARCHAR` exactly.
- **An identity column on PostgreSQL, not `BIGSERIAL`.** `BIGSERIAL` creates a sequence named `chat_messages_id_seq`, which the `schema_filter` regex, naming only the two tables, does not match: `doctrine:migrations:diff` then generated `DROP SEQUENCE chat_messages_id_seq CASCADE`, which would also drop the column default. With `GENERATED BY DEFAULT AS IDENTITY` the diff was empty.
- **Keys are hex and values base64**, so `workflow_store` stays ASCII; 510 characters hold 255-byte identifiers. `updated_at` is required: every write sets it.
- **Strict SQL mode** on MySQL and MariaDB is checked at the first write; both server defaults include `STRICT_TRANS_TABLES`.
- **Not transactional.** MySQL and MariaDB commit DDL implicitly, so the transaction Doctrine wraps a migration in is already closed when it commits: without `isTransactional(): false`, `doctrine:migrations:execute --up` and `--down` each raised `User Deprecated: Context: trying to commit a transaction` on MySQL 8.4 and MariaDB 11.7; with it, none.

Keep the ORM away from these tables, or `doctrine:migrations:diff` and `doctrine:schema:update` propose dropping them:

```yaml
doctrine:
    dbal:
        schema_filter: '~^(?!(chat_messages|workflow_store)$)~'
```

## How it was proven

On SQLite, MySQL 8.4, MariaDB 11.7 and PostgreSQL 17, each in its own database:

1. `doctrine:database:create`, `doctrine:migrations:migrate`, then `doctrine:migrations:diff` and `doctrine:schema:update --dump-sql`: "No changes detected" and "Nothing to update" with the filter; without it, both proposed `DROP TABLE chat_messages` and `DROP TABLE workflow_store`.
2. `doctrine:migrations:migrate first` and back up again on MySQL, MariaDB and PostgreSQL.
3. Through the HTTP server on that database: a JSON turn that called a tool, a turn suspended on an approval, a second turn refused with 409 before any frame, a reload returning the `confirmation` interrupt, and the AG-UI `resume` that executed the tool. Each thread then held 4 user and 4 assistant rows, and `workflow_store` was empty after completion.

When those checks run against a database set through a real env var, make sure it reaches the app: under `php -S`, `.env` wins unless the server starts with `-d variables_order=EGPCS` (the first attempt silently used the SQLite file from `.env`).
